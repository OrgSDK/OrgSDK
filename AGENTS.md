# Development checks

- Follow `CONTRIBUTING.md`: use an issue-linked feature branch and pull request targeting `main`. Keep unrelated changes separate. Do not push directly to main, merge, publish or deploy without authorization.
- Use Bun 1.4 for the server and runtime, and npm in `frontend/`. Run `make install`, `make check`, `make e2e`, and `make build` as appropriate. Browser tests use an isolated temporary data directory. Never point test fixtures at a personal installation.
- Next.js owns the static application, account and setup pages. Bun serves the static export and owns native tRPC, MCP, SQLite, authentication and maintenance. Keep frontend types and API behavior aligned; do not treat historical Django-generated OpenAPI files as a live contract.
- Preserve Tailwind conventions and established product UI. Protect navigation context and unsaved edits. Shared browser tasks follow the workspace `orgsdk-browser` instructions.
- SQLite writes use short immediate transactions. Executors communicate over HTTP only and never access the product database. Network calls must not run inside write transactions.

# Server organization and quality

- Read `server/README.md` for the module map. The application API is native tRPC at `/trpc`, composed in `server/router/index.ts`. Group subrouters by logical product module, with one procedure handler per kebab-case file and an `index.ts` that only composes procedures. Keep `app.ts` limited to application composition. Never add Hono, `/api/...` compatibility routes, method/resource dispatchers, synthetic HTTP calls or REST-forwarding tRPC adapters.
- Keep server TypeScript files at or below 300 physical lines, including comments and blank lines. ESLint enforces this for implementation and tests. Split by responsibility, not arbitrary numbered chunks; extract shared test fixtures when needed.
- Use descriptive names, braces for every control statement, one variable declaration per statement and guard clauses for invalid input. Use the shared Prettier defaults. Run `bun run format` to format server and tooling changes. `bun run check` checks formatting, ESLint and TypeScript; `make check` additionally checks server tests, frontend and runtime. Run `make build`, compiled-binary `make e2e` and `scripts/smoke-binary.sh` for routing, static asset or module-layout changes.
- Procedure callbacks own endpoint-specific business logic and orchestration alongside their middleware and Zod contracts. Do not add a service layer or forwarding function for code used by only one procedure. Extract genuinely shared operations, authorization, validation, public views and query mechanics into logical feature modules or repositories. Shared operations receive `ServiceContext` or explicit dependencies without Request/Response or tRPC. Use shared `ServiceError` codes. Define create inputs as typed objects and update inputs as `{ id, ...changedFields }`; reject unknown fields and use `project` without `agent` aliases. Infer client types from `AppRouter`.
- Use schema-inferred Drizzle models and concrete query modules. Keep query mechanics in feature `queries.ts` files or shared `server/repositories/`, scope resource reads and mutations to the workspace, and push filtering, ordering and limits into SQL. Do not restore generic `any`-typed table dispatch. Keep mutations and their audit records in the same immediate transaction.
- Descriptive names are required; do not use single-letter business variables. Explicit `any` is forbidden throughout the server, including tests, scripts and end-to-end tests. The same gate also forbids unsafe `any` assignment, arguments, calls, property access and returns. Use `unknown` at external boundaries and validate it with Zod or a checked type guard. Never substitute unchecked assertions or lint suppressions. Credentials, repositories and schema modules use strict type-aware ESLint rules.
- tRPC context injects the authenticated `userId`, workspace/membership and procedure type. Mutation CSRF and authorization use procedure semantics, including batches. Application context exposes `db` through the typed Drizzle interface, plus an encryption service. Never pass Store or native SQLite into request/business logic, import `bun:sqlite` there, or reach through Drizzle to `$client`. Native access is limited to database lifecycle, migration inspection and physical backup operations. Use `inTransaction` and pass the transaction context onward for atomic writes; do not use native SQLite transactions.
- Shared feature operations receive data/permissions and explicit dependencies, without Request, Response or tRPC. Query modules receive the Drizzle database and workspace ID. Select public fields explicitly so encrypted secrets cannot escape in response objects. Scope reference/existence checks in SQL and perform checks and writes in the same transaction when they must be atomic.
- Drizzle models in `server/db/schema/` are the database schema source of truth, including defaults, foreign keys, indexes and checks. Generate migrations with `bun run db:generate --name <change>` and review the generated SQL and snapshots. Never add a handwritten bootstrap schema, edit applied migrations, or use schema push. `bun run db:check` verifies that migrations match the models.
- This is a greenfield database with a fresh migration history. Do not add compatibility with the earlier experimental schema or a Django installation. Test fresh creation and upgrades between generated migrations, including data preservation and rollback after failure. Never modify personal installation data during tests.

# External protocol boundaries

- Frontend API calls use `frontend/src/api/trpc.ts`, with inputs and outputs inferred from `AppRouter`. Never add generated OpenAPI types, handwritten response contracts, or REST compatibility calls.
- MCP calls native tRPC procedures. OAuth provider callbacks, authenticated webhook deliveries and the separate executor wire protocol retain dedicated transport adapters; their management APIs are tRPC. Preserve the executor boundary and protocol unless the user explicitly includes the executor in a change. Health checks call `system.health` through tRPC.

# Product boundaries

- Local product: projects have persistent executor folders; external clients own reasoning and conversations. Plugins are external and project-owned. Do not add hosted billing, cloud provisioning or bundled integrations.
- Workspace hostnames select a registered workspace and membership authorizes access. Scope every query and related resource. Enforce permissions in the server, not only the frontend.
- Executor capabilities are scoped to immutable run snapshots. Current project grants further constrain access; changes cannot widen existing snapshots. Keep credentials, registration secrets and approvals outside job authority.
- Preserve immutable action versions, test and validation isolation, protocol compatibility, third-party license notices and runtime vendor provenance.
- SQLite migrations run at startup or through `bun run db:migrate` / `orgsdk migrate`; the compiled executable embeds the generated migration files. Refuse unmanaged or mismatched migration histories. Snapshot SQLite safely and preserve encryption keys and executor data separately.
